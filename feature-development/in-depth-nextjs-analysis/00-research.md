Most Problematic Next.js Anti-Patterns (2024–2025) for Static Analysis

Next.js 13–15 introduced the App Router with React Server Components, streaming, and other paradigm shifts. While these innovations improve performance and DX, they also brought new pitfalls. Below we detail the most problematic anti-patterns observed in Next.js projects (covering both the legacy Pages Router and the new App Router), focusing on issues that static analysis tools can detect. Each section outlines common mistakes, why they are harmful (performance, maintainability, or security), and how to fix them. Code examples are provided for clarity, along with hints for lint rules, auto-fixes, or codemods where applicable.

1. Server–Client Boundary Pitfalls

Next.js App Router defaults to Server Components, requiring explicit 'use client' directives for interactive components. Misunderstanding this boundary is a frequent source of bugs:
• Overusing the "use client" Directive: Marking too many files as client components needlessly shifts rendering to the client, hurting performance. For example, adding 'use client' to a page that only renders static content is an anti-pattern ￼ ￼. Why? Server-side rendering is faster and avoids shipping unnecessary JavaScript.

```javascript
// ❌ Anti-Pattern: Unnecessary client component
'use client'; // (Not needed here)
export default function HomePage() {
  return <h1>Welcome to our site</h1>;
}

// ✅ Fix: Use a Server Component for static UI
export default function HomePage() {
  return <h1>Welcome to our site</h1>;
}
```

Static analysis tip: Flag files using 'use client' but containing no interactive hooks or browser-only APIs. Developers should “only use 'use client' for interactivity (e.g. state or effects)” ￼. A lint rule could suggest removing the directive if no client-only code is present.

    •	Missing "use client" When Needed: The converse mistake is forgetting the directive on components that do use client-only APIs. For example, using React state or useEffect in a file without 'use client' will break, since by default those files run as Server Components (where hooks like useState are unsupported ￼ ￼). A common migration issue is using window or localStorage in a component assuming it only runs on the client – but in Next 13+ even client components render on the server initially ￼. This leads to ReferenceErrors for window or crashes because localStorage is undefined on the server. The solution is to mark such components with 'use client' or use dynamic import with `{ ssr: false }` for truly client-only pieces.

Static analysis tip: Detect usage of browser globals (window, document, localStorage, etc.) or React state/effect hooks in files not marked as client. The linter can suggest adding 'use client' at the top of the file in such cases. For instance, a rule could catch accessing localStorage in a component without use client and recommend wrapping that logic in useEffect or enabling client-side rendering.
• Non-Serializable Server Props/State: In the Pages Router, data passed from getServerSideProps/getStaticProps must be JSON-serializable. A classic anti-pattern is returning values like undefined, Date objects, class instances, or functions in the props. This will cause build or runtime errors: e.g. “Error serializing .artists returned from getServerSideProps… undefined cannot be serialized as JSON. Please use null or omit this value.” ￼. Next.js transfers props via JSON.stringify, so any non-JSON data will break ￼. For example:

```javascript
// ❌ Anti-Pattern: Returning undefined (or non-JSON data) in getServerSideProps
export async function getServerSideProps() {
  const data = await fetchData();
  return { props: { result: data, timestamp: undefined } };
  // 'undefined' will cause a serialization error
}
```

Solution: Sanitize or remove non-serializable values. Convert Date to string (e.g. ISO timestamp), replace undefined with null, and ensure objects are plain JSON. In the example above, use timestamp: null or exclude that field ￼. Static analysis can heuristically flag obvious cases: e.g. returning new Date() or including functions in props. A codemod or ESLint rule might suggest using toISOString() on Dates or recommend libraries like superjson for complex serialization. (Next.js itself now surfaces these errors during development.)

    •	Improper Mixing of Server and Client Components: Another anti-pattern is treating Server and Client Components as if they were interchangeable. For instance, trying to pass a server-only value or function as a prop to a Client Component can fail because such values can’t be serialized across the boundary. Similarly, importing server-only modules (like Node’s fs or a database client) into a client component is a serious mistake – the bundle will either fail to build or include code that can’t run in the browser. Next.js provides safeguards (e.g. the server-only package to mark modules that should never import into client code) ￼ ￼.

Example: Suppose you have a client component for a form, and you import a server utility for database access into it. This will inadvertently bloat the client bundle or throw an error, since database code can’t execute in the browser. The correct approach is to call that logic via an API route or Server Action, not directly inside the client component.
Static analysis tip: Detect imports of known server-side modules or Node built-ins in files with 'use client'. A lint rule can maintain a denylist (e.g. fs, path, database libraries) and prompt the developer to refactor such code into a Server Component or API route. Conversely, if a Server Component attempts to use a React hook like useState or a browser global (which indicates it should be client), that should be flagged (as discussed above).
• Context and Provider Misplacement: In the App Router, one cannot use React Context in a Server Component directly – context providers must be client components. A common anti-pattern is trying to wrap the app in a context provider defined in a server file (or not wrapping at all, expecting old \_app.js to handle it). This fails because server components can’t hold interactive state or context. The fix is to move the provider into a separate 'use client' component and include it in a parent layout. For example, to share theme via React Context, define a Client component ThemeProvider that uses createContext and wraps children, then use it in your root layout around the rest of the app ￼ ￼. This pattern ensures the context is available to all client components down the tree ￼ ￼.
Static analysis tip: A rule could flag context creation or usage in server files. For instance, if it sees createContext() or `<SomeContext.Provider>` in a file without 'use client', it can warn that context providers should live in client components ￼. Automated fixes might not be straightforward here, but the tool can guide the developer to move that code to a client module.

In summary, robust static analysis should enforce clear server-client separation. It can suggest removing unneeded 'use client' directives to reduce bundle bloat ￼, adding the directive where required, avoiding improper prop passing, and preventing accidental exposure of server internals to the client. These measures ensure that developers leverage Next.js’s server rendering benefits without crossing the wires between server and browser contexts.

2. Configuration and Routing Anti-Patterns

Next.js configuration (in next.config.js) and routing conventions have evolved, and outdated patterns can lurk undetected. Static analysis can catch many of these:
• Using Deprecated next.config.js Options: Next.js 13+ deprecated or removed several config options. For example, the target property (used to specify “serverless” builds, etc.) is no longer supported and will error out ￼. Similarly, Next.js 14 fully removed the next export command in favor of setting output: 'export' in the config ￼. If a project still calls next export or relies on old config flags (exportPathMap, etc.), that’s an anti-pattern post-2024. Static analysis can detect known deprecated keys in the exported config object and warn. For instance, if next.config.js contains `{ target: "serverless" }`, the tool should flag it and suggest removal (as the build will fail with a “target no longer supported” message ￼). Likewise, using the legacy @next/font package is outdated – Next 13 introduced built-in next/font, and Next 14 removed @next/font entirely (a codemod exists to update imports) ￼. A migration lint can detect import `{ X }` from '@next/font' and suggest switching to next/font. In short, any config or API marked deprecated in Next 13–15 (such as older image component imports, experimental flags that are now default, etc.) should be surfaced to developers for cleanup.
• Invalid HTTP Method Declarations in Route Handlers: With the App Router, API routes are replaced by Route Handlers (app/&lt;route&gt;/route.js). Each file can export functions for specific HTTP methods (GET, POST, PUT, etc.). A common mistake is misnaming or mis-declaring these handlers. For example, exporting an async function called get (lowercase) instead of GET will simply be ignored – Next.js expects capitalized method names ￼. Calling an unsupported method or spelling it incorrectly leads to 405 errors (Method Not Allowed) ￼. Another anti-pattern is exporting a default handler and named handlers in the same file (or otherwise conflicting route definitions). Next.js rules: you may export one function per HTTP verb, or a default (export default function handler(req, res)) for a wildcard handler, but not both at the same path ￼. Static analysis can enforce these conventions: it should flag unknown export names in route.js files and suggest the allowed ones (GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS). It could also catch the scenario of a pages/api route being mistakenly placed in app/api (which requires the new format), or a leftover default export in an app route file. By guiding proper method exports, the tool prevents subtle bugs where a developer thinks an API is implemented, but Next.js isn’t invoking it due to naming issues.
• Pages/App Router Configuration Confusion: When migrating, it’s easy to mix up behaviors between the old Pages Router and the App Router:
• Routing and Layout config: In Pages Router, files like pages/404.js or pages/500.js defined error pages. In the App Router, this is an anti-pattern – you should use the special not-found.js and error.js files within the app directory (or let Next handle 404s). Developers sometimes mistakenly create app/404.js thinking it will catch 404s; instead it causes build errors ￼ ￼. Static analysis can detect 404.js or 500.js under app/ and warn: "Remove this – use app/not-found.js or app/error.js for error handling." Similarly, \_app.js and \_document.js are ignored by the App Router. If those files linger after migration (or if one tries to use them along with app/), it's a no-op or a source of confusion. A migration rule could remind that global styles should go in app/globals.css and global layout in app/layout.js (with `<html>` and `<body>` tags), rather than using \_app/\_document. Any use of next/head in the App Router is also a sign of a mix-up – next/head is meant for Pages, whereas App Router uses the `<head>` export or React metadata API. Linters can flag import Head from "next/head" inside the app directory and suggest using the new `<Head>` component or the file-based head.tsx convention.
• Route and Link handling: In Next 13+, the preferred navigation in App Router is via the next/navigation hooks (useRouter, usePathname, etc.) and `<Link>` from next/link (which no longer requires an `<a>` child). Using next/router (the old router) inside app/ is an anti-pattern – it won't work. Static analysis should catch import \{ useRouter \} from 'next/router' in an App Router context and point to next/navigation usage ￼ ￼. The same goes for any legacy routing hooks or methods that have changed.
• Misconfiguring Asset Serving and Base Paths: While not as common, config issues like improper basePath or trailingSlash settings can lead to broken links if not applied consistently. Another category is custom webpack config misuse – for instance, some projects still use next.config.js to manually configure Babel/webpack in ways that conflict with Next’s defaults. An advanced static analysis could detect known bad patterns (like using babel-loader in Next 12+ which already uses SWC by default, or overriding Webpack configs in a way that breaks HMR). Additionally, if a project is migrating to static export (output: 'export'), certain features (ISR, dynamic routes without fallback, etc.) are invalid – a tool could warn if it sees output: 'export' alongside usages of getServerSideProps or dynamic routes that aren’t explicitly handled, since those will not work in a fully static build.

In summary, a static analysis tool should act as a guardian against stale config and routing misusage. By flagging deprecated config fields, incorrect route handler definitions, and cross-version mix-ups (pages vs app conventions), it prevents many deployment-time surprises. Most of these fixes can be automated or at least precisely suggested (e.g. “Remove target; Next 13+ defaults to server environment ￼”, “Replace next export with output: 'export' in config ￼”, “Rename function get() to GET() in route.ts for Next to recognize it”).

3. Data Fetching Anti-Patterns

Next.js offers multiple data fetching strategies: SSR (Server-Side Rendering), SSG (Static Generation), ISR (Incremental Static Regeneration), and now React Server Components with async/await and Server Actions. Anti-patterns emerge when developers misuse these, often resulting in slower apps or redundant network calls:
• Fetching Data on the Client When Server Rendering Is Better: A prevalent anti-pattern (especially among those used to pure React SPA development) is to fetch initial page data inside client-side useEffect. In Next.js, this forfeits the advantages of SSR/SSG – the page might render "empty" on the server and then populate on the client, hurting performance and SEO. For example, consider a profile page that fetches user data with a useEffect in a 'use client' component:

```javascript
'use client';
export default function UserProfile() {
  const [user, setUser] = useState(null);
  useEffect(() => {
    fetch('/api/user')
      .then(res => res.json())
      .then(data => setUser(data));
  }, []);
  // ...
}
```

This approach delays rendering until after hydration and duplicates work – the server could have fetched that data before sending HTML. The recommended pattern is to use Next’s data fetching methods: in the Pages Router, use getServerSideProps or getStaticProps to supply the data; in the App Router, fetch data directly in an async Server Component (or use generateStaticParams for SSG). By doing so, the HTML is pre-populated with data, improving load time and SEO ￼ ￼. Static analysis can detect a useEffect that calls fetch() (or Axios, etc.) without dependencies – a strong indicator of an on-mount data load. The linter could then suggest moving that logic to a server function. Some tools may auto-generate a getServerSideProps stub or an async component wrapper. In the example above, the fix is to fetch /api/user on the server side and pass it as prop or, even better, avoid the extra API call entirely by querying the data directly in a server component (since /api/user itself might just call a database). This leads to the next anti-pattern:

    •	Redundant Internal API Calls (Server-to-Server fetch): A common mistake in App Router is fetching an internal API route from a Server Component. For instance, calling await fetch('http://localhost:3000/api/data') inside app/page.tsx to get data that could have been obtained directly ￼. This introduces an unnecessary network hop and complexity. Both Route Handlers and Server Components run on the server, so you can call the underlying logic directly instead of making an HTTP round-trip ￼. Lee Robinson from Vercel notes this as a top mistake: if you have an API route that just returns some DB data, you should invoke that DB query in the server component itself (or import a shared library) rather than fetch your own API over HTTP ￼. The only time an internal fetch might be warranted is when you want to leverage ISR or caching of a route handler, but often it’s inadvertent. Static analysis can catch strings that look like the app’s own domain or calls to Next’s API routes in server code. It can suggest: “Instead of fetch('/api/data') from a Server Component, call the data function directly (since both run on server) ￼.” A code-mod could even replace that pattern if the internal logic is importable.
    •	Waterfall Data Fetching: Related to the above, an anti-pattern is performing sequential data requests that could be done in parallel. This often happens in getServerSideProps or in an async Server Component when developers await one fetch, then another, then another. This waterfall slows down the overall page render linearly ￼ ￼. For example, a dashboard page might do:

// Sequential (waterfall) – ❌ Anti-pattern
const revenue = await fetchRevenue(); // wait for revenue
const latestInvoices = await fetchLatestInvoices(); // then wait for invoices
const metrics = await fetchSummaryMetrics(); // then wait for metrics

If these calls are independent, this is inefficient. The better approach is to start them in parallel (e.g. using Promise.all) ￼. In Next.js App Router, since server components can use top-level await, you can still structure it in a single async component, but ensure to concurrently kick off the fetches. For instance:

// ✅ Use Promise.all for parallel fetching
const [revenue, latestInvoices, metrics] = await Promise.all([
fetchRevenue(), fetchLatestInvoices(), fetchSummaryMetrics()
]);

This can dramatically cut load time by avoiding serial waits ￼ ￼. Static analysis can detect a pattern of consecutive await fetch(...); await fetch(...); await fetch(...); and suggest using parallel techniques. It might even provide an autofix that wraps those calls in a Promise.all([...]). Additionally, Next 13+ has a built-in mechanism to prevent waterfalls in some cases: when using the App Router, you can return multiple Promises from a Server Component and React will resolve them in parallel. However, the developer must be careful not to accidentally introduce a waterfall by awaiting one before starting the next. A lint rule could warn if it sees one await followed by another call that could have been awaited concurrently.

    •	Improper Use of Caching and Revalidation: Next.js App Router introduces granular caching for data fetching. By default, fetch() in a Server Component with a static URL may be cached at build time (like SSG) ￼. Developers unaware of this might be puzzled when an API call doesn’t re-run on each request. Anti-patterns here include expecting dynamic behavior without opting out of caching, or conversely, disabling caching unnecessarily. For example, writing a route handler that fetches external data without specifying any cache control will result in that handler being statically prerendered at build (for GET requests) ￼. If the data needs to update frequently, the developer should mark it dynamic (export const dynamic = "force-dynamic" or use cache: 'no-store' in fetch). Forgetting to do so is a mistake – the page might serve stale data indefinitely, thinking SSR will update it. Static analysis could identify route handlers or server functions that call fetch() and assume freshness: if it sees no caching directive but uses, say, process.env or an API URL that looks non-static, it might warn to review caching (though this is tricky to determine automatically). Another pattern: using ISR (revalidate) in the Pages Router but misconfiguring it. For instance, setting revalidate to 0 (which effectively disables ISR and might be an anti-pattern if the intent was to always fetch fresh data – better to use SSR in that case). Or forgetting to add revalidate at all when static props need periodic refresh. Linting can check if getStaticProps is used without revalidate in a context where maybe it should (though that might be speculative).

A new aspect in Next 13+ is Server Actions (stable in Next 14) for mutations. After a mutation, one should revalidate or refresh the client state. A common oversight (anti-pattern) is updating the database on the server but not updating the UI. For example, a form Server Action that saves data to DB but doesn’t refresh cache means the page might still show old data. Next provides utilities like revalidatePath() or router.refresh() on the client. Static analysis could remind: if a server action function (marked with 'use server') is calling a mutation (e.g. writing to a DB or calling an external POST) and the same file or component has no follow-up revalidation logic, suggest adding one. The Vercel team specifically calls out “Not revalidating data after mutations” as a common mistake ￼. A heuristic could be: in an action, after performing a mutation, ensure a call to revalidatePath/revalidateTag (for App Router) or that the client triggers a refresh.
• Neglecting Suspense and Loading States: With React 18 and Next.js streaming, not using Suspense boundaries or the app/(loading.jsx) files is an anti-pattern that affects UX. In the App Router, if you have an async component fetching data, Next will stream the shell and then the content when ready. If no loading state is provided, the user might see a blank area. A better pattern is to wrap slower parts in Suspense with a loading fallback or to use the built-in segment-based loading file (e.g. app/dashboard/loading.js to show a loading indicator while the dashboard page is streaming in). A common mistake is placing Suspense in the wrong spot – e.g. around a parent server component rather than around the specific slow component, resulting in a suboptimal loading sequence ￼. Another is forgetting to include an error.js boundary to catch errors in deeply nested components, causing unexpected error bubbles or console warnings. While these issues are somewhat harder to detect statically, a tool could at least detect the absence of loading and error states for major routes. For example, if a page component makes multiple fetches and is not wrapped in Suspense, a warning could be issued: "Consider adding a Suspense boundary to avoid blocking the entire UI during data load." Similarly, if a project has no loading.js files at all in the app directory, the tool might suggest using them for better UX on slow connections.
• Ignoring Server Actions (or Misusing Them): Server Actions allow directly calling server-side code from client components (via forms or useOptimistic hooks), eliminating the need for many API routes. An anti-pattern in 2024 is to stick to old habits – e.g. building a /api/submitForm route and then using fetch in a client component’s onSubmit handler, instead of using a form action=`{serverAction}` which is simpler and more secure. If static analysis sees a form in JSX that does a client JS onSubmit with fetch, it could suggest using a Next.js Server Action for a progressive enhancement approach. Another misuse is placing server actions in the wrong context – e.g. trying to call a server action from a Server Component (which is pointless, since you could just run the code directly), or trying to use a server action in an environment where it’s not allowed (like outside a React tree). Linters can ensure that use server functions are only defined in files that are imported into client components, and that they are not called like regular functions in server code.

In short, data-fetching anti-patterns often revolve around doing things on the client that could be done on the server (or at build time), or doing things sequentially that could be parallel. Static analysis should nudge developers toward Next.js’s strengths: SSR/SSG for initial page load, parallel fetching to optimize performance, and the new server-side paradigms (Server Components and Actions) to reduce unnecessary client work. By citing these anti-patterns (e.g. “Fetching JSON from a Route Handler in a Server Component – just call the logic directly! ￼”), the tool can educate as it warns. Many of these can be auto-fixed or at least precisely pinpointed, making it an ideal target for advanced lint rules.

4. Security Anti-Patterns

Security issues can be subtle, but static analysis is a powerful aid to catch certain patterns in Next.js apps that commonly lead to vulnerabilities or leaks. As Next.js applications often handle sensitive data, it’s critical to avoid these anti-patterns:
• Exposing Secrets to the Client: Next.js distinguishes between server-only environment variables and those exposed to the client. Only env vars prefixed with NEXT*PUBLIC* are sent to client-side bundles ￼. A major anti-pattern is using a secret API key or database URL in client-side code, thinking it will be kept secret. For example, process.env.DB*PASSWORD used inside a React component will be undefined on the client (if not prefixed) or, worse, in certain cases Next might inline it at build time (thus leaking it). Static analysis should scan for process.env usages in client files. If it’s a server-only variable (no NEXT_PUBLIC*), raise a red flag – this likely represents an attempt to use a secret on the client. The fix is to move that logic to an API route or Server Action so the secret stays on the server, or if the value truly needs to be on the client (rare for secrets), rework the approach entirely. The Next.js Security Checklist notes that environment variables should be treated carefully: even on server, they can leak via logs or misconfigurations ￼. Using a secrets manager is recommended for real production secrets ￼, but at minimum, do not bundle them in client code. A static analyzer could even integrate with a tool like TruffleHog to detect API keys or secrets committed in the repo (outside the code logic).
• Unsanitized HTML Content (XSS vulnerabilities): React by default escapes content, but when developers bypass this via dangerouslySetInnerHTML or direct innerHTML assignments, they can introduce Cross-Site Scripting (XSS) if the content contains malicious scripts. It’s an anti-pattern to use dangerouslySetInnerHTML with raw user input or without a proven sanitization step. The usage of this API is, by definition, dangerous ￼ – if a static analyzer finds it, it should demand justification. For example:

```jsx
// ❌ Anti-Pattern: Inserting unsanitized HTML
<div dangerouslySetInnerHTML={{ __html: userProvidedHTML }} />
```

If userProvidedHTML is not sanitized, an attacker could inject `<script>` tags. The tool should flag any dangerouslySetInnerHTML and ideally require a comment or function call indicating sanitization (e.g. using a library like DOMPurify). Similarly, using element.innerHTML = ... in client-side code is risky ￼. The Arcjet security guide explicitly warns: “Any use of dangerouslySetInnerHTML is a risk… It allows injecting raw HTML, bypassing React’s protections, opening the door to XSS” ￼. It even suggests preferring .innerText or other safer alternatives when inserting text content ￼. So a lint rule might suggest: if you truly must set HTML, ensure the source is sanitized or constant. Otherwise, avoid it. Often there’s a better pattern (e.g. use Markdown rendering libraries that sanitize, or build the DOM with React elements).

    •	Improper Redirects and URL Handling: One subtle security pitfall is constructing redirects using untrusted input. For instance, reading a ?next= query parameter and redirecting the user to that value can lead to open redirect vulnerabilities (where attackers trick users into visiting malicious sites via your domain). Next.js provides safe redirect patterns (like returning `{ redirect: { destination, permanent }` } from getServerSideProps or using NextResponse.redirect in middleware). However, if destination is derived from user input, it should be validated (e.g. ensure it’s a path within your site). Static analysis might not fully understand the intent, but could warn if it sees something like res.writeHead(302, `{ Location: userUrl }`) or redirect(req.query.next) without sanitization. Another redirect-related anti-pattern specific to Next 13 App Router: calling the redirect() function from next/navigation inside a try/catch. As noted by Vercel, redirect() works by throwing a special error internally ￼ ￼. If you wrap it in a try/catch, you’ll catch that error and prevent the redirect ￼ ￼. So the correct usage is to call redirect() outside of error handling blocks (or re-throw it). A static analyzer can detect redirect( inside a catch block and flag it, citing that it should be done before or after the try/catch, not within ￼ ￼. This is a logical bug that could lead to users not being redirected when they should (e.g. on auth failure). The fix is to restructure code so that redirect('/login') is called after a failed fetch or auth check, but not from inside a caught exception.
    •	Authentication and Authorization Flaws: Authentication in Next.js (often using libraries like NextAuth or custom JWT/session solutions) can have anti-patterns that static analysis might catch. One is relying purely on client-side checks for protected pages. For example, rendering a page that reads a token from localStorage and redirects to /login if not present. This is insecure because an attacker could bypass it (since the page still gets delivered). The proper approach is to enforce auth on the server side: e.g. use getServerSideProps to redirect unauthenticated users, or use Next.js Middleware to block requests to certain routes. In fact, Next.js Middleware was a common solution for auth, but a 2025 vulnerability (CVE-2025-29927) showed that middleware auth checks could be bypassed by forging a request with an extra header ￼. The lesson (and emerging best practice) is to not rely solely on middleware; ensure route handlers themselves validate the session/token ￼. Static analysis can look for patterns like usage of next-auth or other auth logic and warn if, for instance, API routes don’t verify the user. If an API route receives req.session or a JWT and the code doesn’t check it, that’s a potential open door. Similarly, if middleware is used for auth, perhaps highlight the need to upgrade to a patched Next.js version and double-check that the x-middleware-subrequest header exploit is mitigated ￼. While these are complex to automate, even simple checks help: e.g. flag if (!session) router.push('/login') in a client component – suggest moving that check to getServerSideProps or using the newer generateMetadata with a redirect (in App Router) or server-side redirect() for better security.

Another common anti-pattern is storing JWTs in localStorage (vulnerable to XSS) instead of secure httpOnly cookies. Static analysis might search for references to localStorage.setItem('token', ...) and warn “Storing tokens in localStorage can lead to XSS leaks; prefer httpOnly cookies for authentication data.” This is more of a general web security advice, but certainly relevant in Next.js contexts.
• Unvalidated Inputs in API Routes: API routes and route handlers can be entry points for attacks like SQL injection or JSON injection if inputs aren’t validated. A good practice is to use schemas (e.g. Zod or Joi) to validate req.body and req.query. An anti-pattern is accepting input and directly using it in database queries or rendering. While full code analysis of queries is complex, a static tool could at least flag lack of any validation in critical routes. For example, if a route handler function takes a Request and immediately calls await someDB.query("SELECT \* FROM table WHERE id=" + id) with id coming from searchParams without validation or sanitization, that’s worth a warning. Patterns to encourage include using parameterized queries or ORMs, and using libraries like validator or Zod to sanitize input. We can’t expect the static tool to fully know what’s safe, but it might note when dangerouslySetInnerHTML or eval are used (both are sinks for potential injection) ￼. It’s worth noting Trusted Types (an upcoming standard to mitigate XSS) are not yet supported in Next.js ￼ ￼, so developers must be vigilant manually.
• Omitting Security Headers: Another category, albeit more about configuration: Next.js makes it easy to add custom HTTP headers (via next.config.js headers() function or middleware). Anti-pattern: not using important security headers like Content Security Policy (CSP), Strict-Transport-Security, etc. While not directly a code bug, static analysis could remind if the app lacks any CSP implementation or if X-Frame-Options/CSP’s frame-ancestors is missing in an app that might be loaded in iframes. Tools could integrate with security scanners (or simply check that the Next config or middleware sets some known headers). The Arcjet blog lists essential headers and notes how to set them (via a library or manually) ￼ ￼. For example, no usage of helmet or no Content-Security-Policy might prompt: “Consider adding a CSP header to mitigate XSS ￼.” This is more of a suggestion for advanced tooling.
• Not Using server-only for Sensitive Code: Next.js allows importing server-only code into server components safely, but there’s always a risk a developer might accidentally import something into a client component. The package server-only helps by throwing build errors if misused ￼. Not using it isn’t exactly an anti-pattern, but if your project deals with serious secrets, using import "server-only"; at the top of certain modules (like the module that connects to your database or contains secret logic) is a good practice ￼. Then, if someone inadvertently imports that module into a client component, the build will fail, alerting you. A static analyzer could recommend adding import "server-only" in modules that clearly should never run on client (e.g. files in a /lib/ folder that deal with credentials). This is more of a nice-to-have, but it aligns with defense-in-depth.

In summary, security anti-patterns range from the obvious (XSS via dangerouslySetInnerHTML) to the subtle (improper redirect usage). Static analysis should focus on patterns that are statically detectable with low false-positive rate: secret usage in client code, use of dangerous sinks (eval, innerHTML), missing sanitization, and known incorrect usages of Next features (like catching redirect). Many of these issues are frequently discussed in community forums, as developers often hit them incidentally. By addressing them, we can significantly harden a Next.js codebase. For example, simply flagging all instances of dangerouslySetInnerHTML forces a developer to think: “Do I absolutely need this? If yes, have I sanitized the input?” ￼ – which can prevent a costly XSS bug down the road.

5. Migration and Cross-Version Issues (Pages Router -> App Router)

Upgrading an existing Next.js app (v12 or earlier Pages Router) to the App Router (v13+) is non-trivial. Certain anti-patterns appear during migration when code meant for the old architecture is misapplied to the new. These include:
• Misplaced Files and Missing Conventions: As mentioned, a big migration gotcha is error handling. In the Pages Router you might have had pages/404.js and pages/\_error.js (for 500 errors). If you simply copy those into app/, you’ll break things ￼. The App Router expects special not-found.js and error.js files instead. The anti-pattern is attempting to manually handle 404/500 routes in App Router. Static analysis of an app directory can spot files named 404.jsx or a route defined at /404/page.js – those are incorrect (Next will try to treat /404/ as a regular route, not a global 404). The correct approach is to use the provided error boundary mechanism: create an app/not-found.js that renders a Not Found UI (automatically shown when notFound() is called or a route is missing), and app/error.js to catch errors. Migration guides and community posts emphasize deleting the old 404/500 pages ￼ ￼. A codemod or linter can directly point this out and even refuse to build if such patterns are present.
• Still Using \_app or \_document patterns: In a migrated app, having pages/\_app.js or \_document.js alongside the new app/ directory is usually an indicator that some logic hasn’t been moved. Next.js will ignore \_app.js if an app/ directory exists (since the App Router has its own layout mechanism), and \_document.js is also not used by App Router (the html structure is defined in app/layout.js). If those files include important logic (analytics, context providers, global CSS), an incomplete migration might lead to lost functionality. So, static analysis should warn if \_app.js or \_document.js exist and the app/ directory is present: “Remove or migrate \_app/\_document – App Router uses app/layout.tsx for global wrappers.” For example, global CSS imports from \_app.js need to go in app/globals.css and be imported in the layout; custom Html, Head, Main tags from \_document.js should be reflected in the root layout (Next's codemod often creates a basic layout with html/body structure and children). Also, if \_document set things like `<meta charset>` or Google Analytics scripts, those need to move to the appropriate place (either app/head.js for meta tags or using next/script in the layout for analytics). A thorough static analyzer could detect usage of Head from next/head or `<Script>` in \_document and remind the developer to relocate them.
• Routing Hook Changes: As mentioned, code using next/router needs to switch to the new next/navigation. A migration anti-pattern is not updating these imports, which will break navigation or cause runtime errors. The codemod provided by Next can do some of this, but static analysis can catch any stragglers. For example, useRouter() from next/router should become useRouter() from next/navigation (which has a slightly different API). The tool can auto-replace the import and adjust calls if needed. Similarly, next/link no longer needs an `<a>` child – a minor change, but if someone keeps the old pattern, it still works (Next will strip out the extra `<a>`). It’s not harmful, but a lint could suggest removing the redundant `<a>` as a cleanup (since Next 13+ Link automatically renders one ￼ ￼).
• Data Fetching Migration Issues: Pages Router used getStaticProps, getServerSideProps, etc., whereas App Router uses direct async components or generateStaticParams. An anti-pattern is trying to use old data fetching methods in the app directory – e.g. writing export async function getServerSideProps() inside an app/page.js. This will simply be ignored (the function isn’t used by App Router), and the data won’t load. Static analysis can easily catch keywords getServerSideProps, getStaticProps, getInitialProps in the app directory and throw an error: “getServerSideProps is not supported in the App Router – move data fetching into the component or use an API route.” Conversely, if one is incrementally migrating and still has pages using those methods, ensure they are correct. Another migration anti-pattern is misunderstanding dynamic routes: in Pages, getStaticPaths was needed for dynamic SSG pages; in App Router, generateStaticParams fulfills a similar role. Not implementing it when needed (or vice versa implementing both old and new in the wrong places) can cause 404s. For instance, if a developer migrates a dynamic route but forgets to add generateStaticParams, Next might not pre-render certain paths, leading to runtime fetches or errors. While static analysis can’t easily know if this was intended, it could note when a dynamic [slug] page in App Router has no generateStaticParams and is not marked dynamic (via config) – possibly a hint to review if SSG is desired.
• Static Assets and Public Files: In the Pages Router, anything in /public is served at root path, and Next automatically optimized images via next/image. In App Router, this remains largely the same – the public folder is still used. However, some developers mistakenly try to put static assets inside the app directory, thinking they might be served. For example, putting images in app/images/ and trying to reference them by that path will not work (those files would be part of the build output, not a static file unless you create a route for them). The anti-pattern is misplacing assets. The correct practice is to keep using public/ for images, or import the image for automatic bundling. If migrating, ensure that any references to /public files remain valid. Static analysis might not catch all, but could warn if it sees something like import '/app/assets/logo.png' – which isn’t a module import that Next understands (unless you use import which Next might treat as Webpack asset, but file structure matters). Another related item: Next 13 improved the next/image component (no more next/legacy/image). A migration anti-pattern is failing to update old usage or using layout="fill" (deprecated) instead of the new fill prop, etc. Lint rules can target the image component usage and suggest modern patterns (the Next codemods handle some of this, e.g. adding fill boolean and removing layout prop).
• Font Optimization Migration: As noted, older Next.js auto-inlined Google Fonts CSS (if you used a Google Fonts link in \_document). In App Router, that doesn’t happen; instead they introduced next/font to fetch fonts at build time. An anti-pattern is continuing to include `<link href`="https://fonts.googleapis.com/..." rel="stylesheet"> in your layout without using next/font. It will still load fonts, but you lose the optimization and privacy benefits. Also, if you remove \_document and forget to include that link in the new layout, you might break your font loading. Static analysis can remind: “Use next/font to optimize custom fonts – the old method of linking Google Fonts CSS is not optimized in App Router ￼.” If it detects a Google Fonts URL or finds the project using @next/font (which is now removed), it can prompt to switch.
• Parallel Routes and Nested Layouts: Migrating a complex structure might lead to anti-patterns like duplicating layout code in multiple files (not realizing you can create a shared layout at a higher level). For instance, someone might wrap each page in the same header/footer manually, instead of using a layout file – this is essentially ignoring one of App Router’s strengths. A static analyzer could notice if several page files have the same JSX structure around `<Navbar>` and `<Footer>` and suggest abstracting that into a layout. This is more of a code anti-pattern detection than a strict error, but it improves maintainability. Similarly, not using Route Groups (the (group) folders in Next 13) can lead to awkward file structures. A community anti-pattern noted was “Not Using Route Groups for organization” ￼ – i.e. scattering related routes without grouping. While hard to enforce via code, a documentation or warning could be given if a layout file gets too large or if many routes share duplicates.
• Incremental Adoption Quirks: Next 13+ allows Pages and App Router to coexist (to migrate gradually). However, certain edge cases arise, like linking from an App page to a Pages page might do a full page reload (since the router can’t do a seamless client transition in that scenario). A known issue reported is that mixing the two router types can lead to weird behaviors unless handled carefully ￼. As an anti-pattern, running a hybrid app for too long can be problematic. Static analysis might simply notify if both pages/ and app/ directories are present: “Project is using both Pages and App Router – ensure this is intentional. Consider finishing migration to avoid inconsistent behavior.” This isn’t “wrong” per se, but an encouragement.
• Legacy Patterns No Longer Needed: Lastly, highlight any code that was a workaround for older Next.js versions that is now obsolete. For example, some apps used to manually code-split or manage bundle loading due to older constraints – Next 13+ and React 18 handle a lot of this (with Suspense and the new compiler). Using next/dynamic improperly (like wrapping every component in a dynamic import to try to defer loading, which can actually hurt performance or complexity) can be an anti-pattern unless truly needed. If static analysis sees excessive use of dynamic() for components that aren’t large or are used above-the-fold, it might be worth flagging as over-engineering. Similarly, getInitialProps is a legacy data fetching method from Next 9 and earlier – if a project still has it, that’s a red flag. It was replaced by getServerSideProps/getStaticProps, and it doesn’t work at all in React Strict Mode/Concurrent features. The tool should scream if it finds getInitialProps anywhere, advising to migrate off of it. This often comes up when migrating older Next.js apps (pre-v9.3).

By addressing these migration anti-patterns, static analysis assists developers in upgrading smoothly. Many of these issues are frequently asked about on forums (e.g., “Why is my 404 page not working after moving to App Router?” – Answer: Because you need not-found.js ￼). A linting suite specifically tuned for Next.js 13+ could greatly reduce the pain of migration by catching these mistakes at build time, rather than developers discovering them manually. In combination with official codemods, it ensures no stone is left unturned (for example, codemods handle renaming imports like next/image, but a lint can catch logical issues like missing error boundaries).

⸻

Conclusion: The above categories cover the most problematic patterns observed in Next.js projects circa 2024–2025. They span performance pitfalls, security vulnerabilities, and migration traps – all areas where advanced static analysis can provide value. By integrating rules to detect these anti-patterns, tooling (ESLint plugins, custom codemods, Semgrep rules, etc.) can surface actionable insights to developers. The goal is to encourage best practices: clear separation of server/client concerns, up-to-date configuration, efficient data loading, secure coding patterns, and proper use of Next.js 13+ features. Each anti-pattern, as shown, comes not only with a “❌ Don’t do this” but also a “✅ Do this instead,” which a good static analysis tool should communicate – possibly even automatically fixing straightforward cases.

Adopting these checks will result in Next.js applications that are faster, more secure, and easier to maintain, especially as the framework continues to evolve. By learning from community discussions and frequent GitHub/Reddit questions (many of which revolve around these very mistakes), we can proactively guard against them in our codebases. The end result is a smoother developer experience and more robust applications built with Next.js.
